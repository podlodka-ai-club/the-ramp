## What is the main purpose of project creation

OntoShip gives an AI coding agent — and its human operator — a **persistent, plain-markdown knowledge base (KB) about a codebase**, so that answering "how does X work here / where is it documented" becomes an *indexed search* instead of a blind `grep`/`rg` fan-out.

Its founding bet is *radical simplicity*. `README.md` states it directly: **"A project knowledge base is just `markdown` + a `README` index + `git`. Nothing simpler works better."** There is no service, database, embedding model, or vendor — every derived artifact (the search index, the HTML graph) is regenerated from the markdown on demand, so git history stays clean and the KB can never silently drift from its index.

The project's positioning ADR (`docs/decisions/ontoship-positioning.md`) reframes the goal beyond "search": it is **team experience-transfer for AI-agent development**. The KB is "the substrate that makes this possible (a deterministic md source any human or agent can read); the dev-flow is the method being transferred." The target audience is teams handing off "vibecoded" projects — an operator should be able to pick up a repo and drive work to a PR *the way the original author would, without the author in the loop*. The docs candidly admit the FTS5 search layer is "the weakest layer on the merits" versus a vector index (an explicitly "accepted ceiling").

## Short description of main functionality

OntoShip ships as a Claude Code **marketplace with two plugins** (`.claude-plugin/marketplace.json`):

- **`gitmark`** — the markdown+git KB engine plus a spec-driven development flow.
- **`destructive-guard`** — an orthogonal safety hook (unrelated to memory).

The core engine is **`skills/kb-search/gitmark.py`**, a zero-dependency Python-stdlib CLI (`VERSION = "0.1.0"`). Its subcommands:

- `index` — build the SQLite FTS5 index from the markdown.
- `search` — ranked results merging bm25 ∪ trigram ∪ fuzzy passes.
- `map` — emit a self-contained HTML tree with rendered markdown and a radial link graph.
- `serve` — a local HTTP viewer.
- `stat`, `lint` (ontology invariants I1–I6), `version`.

Five **slash commands** (`commands/*.md`) are thin wrappers over the skills/CLI:

- `/kb <query>` — refresh index, `search -k 8`, answer from the top hits.
- `/kb-map [path]` — build the HTML graph.
- `/doc <topic>` — compose/update **one** KB doc following the ontology (searches first to avoid duplicates).
- `/onto-doc [scope]` — bootstrap/rebuild the **whole** KB by fanning out one curator subagent per area, then lint + index + map.
- `/ship <change>` — run the gated development flow.

Three **skills** encode the agent's behavior: `kb-search` (search instead of grep), `kb-curate` (ontology rules for adding/editing docs), and `dev-flow` (research → tasks → goal → spec → git worktree → implement → tests → independent review → dev-tests → prod-tests → ship via MR → `dev` → `main`).

## How it works under the hood

**Tech stack.** Pure Python ≥3.7 standard library. The only optional dependency is the `markdown` package, used solely to render docs in the HTML map; without it, docs display as raw `<pre>` (`gitmark.py:451-456`). The derived store is **SQLite FTS5**.

**Data flow** (per `docs/reference/architecture.md`): a user types a slash command → `commands/*.md` delegates to a skill → the skill calls `gitmark.py` → the CLI reads/writes the markdown KB and regenerates derived artifacts. Crucially, only the markdown is committed:

| Artifact | Derived from | Lives in | Regenerated by |
|---|---|---|---|
| `index.db` (SQLite FTS5) | the `.md` files | `.gitmark/` (gitignored) | `gitmark index` |
| `docs-map.html` | `.md` files + links | wherever pointed | `gitmark map` |

`.gitignore` excludes `.gitmark/` and `*-map.html`, so "derived artifacts never live in git — you just re-run the CLI."

**Indexing** (`cmd_index`, `gitmark.py:139-198`). `iter_md()` walks every `*.md` (skipping `EXCLUDE_DIRS` like `.git`, `node_modules`, `.gitmark`). Each file gets a `title` (first `# H1` or filename) and an `area`. `chunk_md()` splits a file at markdown headings into `(line_start, heading, body)` chunks — the indexed unit and the granularity of the `path:line` results. Chunks are inserted into two FTS5 virtual tables: `fts` (`tokenize='unicode61 remove_diacritics 2'`, bm25 ranking) and `tri` (`tokenize='trigram'`, substring/fuzzy — only if the SQLite build supports it, probed by `_has_trigram`). Supporting tables: `files`, `links(src,dst)`, `meta`.

**Search** (`cmd_search`, `gitmark.py:227-292`) merges up to three passes keyed by `(path,lineno)`, with stronger passes winning collisions: (1) **bm25** prefix-`OR` match at full weight; (2) **trigram phrase** exact substring at ×0.6; (3) **fuzzy** — `_fuzzy_phrases()` breaks words ≥4 chars into overlapping 4-char windows, OR-matched, accepting a chunk only when it contains ≥`need` distinct windows (≈20%), at ×0.3. This is what makes typos, morphology, and Cyrillic tolerable (the comments cite `firecraker`↔`firecracker`).

**Plugin/hook wiring.** `.claude-plugin/plugin.json` defines `gitmark`; the separate `destructive-guard` plugin registers a `PreToolUse`/`Bash` hook (`destructive-guard/hooks/confirm-destructive.py`) that forces a y/n confirmation on `rm`, `git reset --hard`, SQL `DROP/TRUNCATE`, etc. without false-positiving `perform`/`terraform`. It is well tested (`tests/test_hook.py`).

## How memory about a codebase under development is implemented

**What the memory *is*.** In the survey's terms, OntoShip is **token-level, factual/experiential memory** — *not* parametric (nothing is fine-tuned) and *not* latent (no embeddings/vectors). Memory is stored as **human-readable markdown files** that are injected verbatim into the agent's context window. There is no dedicated working-memory abstraction; the "memory" is a durable, external, git-versioned corpus the agent searches and reads on demand.

**Format and location.** Memory is the `docs/` tree plus every `README.md` and any `*.md`. The canonical shape (`README.md`, `CLAUDE.md`):

```
CLAUDE.md / AGENTS.md          ← entry point
/docs
  README.md                    ← master index
  /services/<service>/README.md   ← always the folder index
```

`CLAUDE.md` is the entry point; each folder's `README.md` is its index. Markdown is the **source of truth**; the SQLite index (`.gitmark/index.db`) and `docs-map.html` are derived caches, never committed.

**Structure — the ontology (the distinctive part).** `docs/ontology.md` defines a lightweight "code-ontology" explicitly modeled on **Palantir Foundry/Gotham**: every doc is a typed **object** (a `node_type`), with **properties** (YAML frontmatter) and **typed links**. This is how factual memory ("what the billing service is") and experiential memory (a `decision`/ADR, a `gotcha`, a dev-flow `spec`) are distinguished — via `node_type`:

- Node types (`gitmark.py:312-313`): `service`, `reference`, `runbook`, `gotcha`, `decision`, `plan`, `guide`, `report`, `index`, plus `memory` (accepted by the linter but not documented in the ontology's node_type table — a small observed inconsistency).
- Link types (`docs/ontology.md`): `documents`, `depends_on`, `supersedes`, `relates_to`, `implemented_by`, `part_of`. The **doc→code links** (`documents`/`implemented_by`, e.g. `documents: [../../src/billing]`) are what tie the memory to the code it describes — "what makes this an ontology *over code*." Example: `docs/services/gitmark-cli/README.md` links to `../../../skills/kb-search/gitmark.py`.

**How memory is written/updated (lifecycle).** The `kb-curate` skill (`skills/kb-curate/SKILL.md`) is the write path:

- **CREATE:** search first (don't duplicate) → pick `node_type` + folder → write frontmatter (`node_type`, `title`, `service`, `status: active`, `updated: YYYY-MM-DD`) → add ≥1 typed link (no orphans) → add a line to the folder `README.md` index.
- **UPDATE:** bump `updated:`; when stale, set `status: deprecated` and add `supersedes:` on the replacement.
- **MOVE:** `git mv` (preserves history) + rewrite links.
- **REINDEX:** always end with `gitmark lint` then `gitmark index`.

Two write flows exist: `/doc` (one doc) and `/onto-doc` (bootstrap the whole KB by fanning out curator subagents). The **dev-flow** closes the loop: its spec stage writes each feature spec *into the KB via kb-curate* — "durable knowledge, not a throwaway ticket" — so every shipped change leaves an ontological, code-linked document. Memory is thus co-produced with the code rather than bolted on afterward.

**Invalidation / integrity.** `gitmark lint` (`cmd_lint`, `gitmark.py:361-444`) enforces invariants I1–I6: valid frontmatter (I1), vocabulary-conformant values (I2), no orphans (I3, ≥1 in/out link), no broken links (I4), a README per `docs/` folder (I5), and `supersedes` targets marked deprecated/archived (I6). This is how the KB "doesn't rot into a pile of files" as it grows. Staleness is handled *socially* (`status`, `updated`, `supersedes`) rather than by TTL; the index itself is a disposable cache rebuilt on every `index` run.

**How it is retrieved and injected into context.** Retrieval is `/kb` → `gitmark search` (the three-pass FTS5 merge), returning ranked `path:line · heading · snippet`. The command instruction (`commands/kb.md`) is explicit: *"Summarize the top hits… don't reprint whole snippets. Open the 1–2 most relevant files and answer."* Injection is therefore **two-stage**: search narrows to exact `file:line` locations; the agent then `Read`s those specific spots.

**How it reduces `find`/`rg`.** The chunk-level `path:line` index replaces recursive filesystem scans with a single ranked query that tolerates substrings, typos, morphology, and non-Latin scripts (the fuzzy 4-gram windows) — cases `grep` handles poorly. The agent gets pre-curated, human-authored *prose about intent and architecture* (not just literal code matches), and the `documents`/`implemented_by` links point straight from a concept to its source files. The `gitmark map` graph (BFS-laid-out from the `CLAUDE.md` entry node; ring = distance-from-entry) additionally lets a human or agent navigate the knowledge topology visually. Net effect: the agent reads a small, relevant, typed slice of durable memory instead of grepping the tree blind.
