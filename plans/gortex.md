## What is the main purpose of project creation

Gortex exists to give AI coding agents a persistent, queryable **model of a codebase under development** so they stop burning tokens on blind `find`/`rg`/`grep`/`Read` exploration. The README describes it as a "High-performance and efficient code-intelligence engine for AI agents and IDEs" (`README.md:8`) that produces "a persistent provenance-tiered knowledge graph of functions, classes, call chains, HTTP routes, and cross-service contracts" (`README.md:29`). The stated payoff is concrete: one `smart_context` call "replaces 5-10 exploration calls" (`docs/mcp.md:218`), for **up to 50× fewer tokens per response** (`README.md:29, 45`).

The problem it solves is that agents rediscover a repository's structure on every task and after every context-window compaction, which is slow and token-expensive. Gortex indexes the repo **once** into a structural graph (files, symbols, calls, imports, contracts) and serves precise slices of it on demand. Its audience is AI coding assistants — the README lists **18 supported agents** (Claude Code, Kiro, Cursor, Windsurf, VS Code/Copilot, Continue.dev, Cline, OpenCode, Antigravity, Codex CLI, Gemini CLI, Zed, Aider, Kilo Code, OpenClaw, Hermes, Oh My Pi, Pi; `README.md:32`) — plus the humans running them. Design constraints are deliberately practical: **zero dependencies**, a single static binary, everything in-process and in-memory, no external services (`README.md:10, 29`).

## Short description of main functionality

A user runs two setup commands: `gortex install` once per machine (writes user-level MCP config, tool-usage skills, slash commands, hooks) and `gortex init` once per repo (writes `.mcp.json`, `.claude/settings.*`, a generated `CLAUDE.md` overview, per-community `SKILL.md` files). See `README.md:75-127`.

The agent then gets **175 configurable MCP tools** (100+ enabled by default; "use only what you need," `README.md:29, 52`) over stdio. The headline ones:

- **`smart_context`** — task-aware minimal context that "replaces 5-10 exploration calls," always emitting a `blast_radius` block and a file-clustered `working_set` (`docs/mcp.md:218`).
- **`search_symbols` / `get_symbol` / `get_symbol_source`** — replace Grep/Read; `get_symbol_source` reports `tokens_saved` per call.
- **Traversal**: `get_callers`, `get_call_chain`, `find_usages`, `find_implementations`, `get_dependents` (blast radius).
- **`get_editing_context`**, `edit_symbol`, `rename_symbol`, `edit_file`, `write_file` — read-free editing.
- **`analyze`** (dead code, hotspots, cycles), **`contracts`** (cross-repo HTTP/gRPC/GraphQL/topic matching), **`get_communities`** (Louvain clusters), **`feedback`** (agent reports which symbols were useful/missing).
- **`plan_turn`** — a ~200-token "opening-move router" that ranks the next tool calls for a task (`internal/mcp/tools_planning.go:21-30`).

There are also **16 MCP resources** (URI-addressable state like `gortex://stats`, `gortex://communities`), **3 prompts** (`pre_commit`, `orientation`, `safe_to_change`), a CLI (`gortex query symbol/deps/callers/...`, `gortex index`, `gortex savings`), an HTTP `/v1/*` JSON API (`gortex server`), and an optional long-living **daemon** holding one shared graph for all agent windows over a Unix socket. Semantic search is default-on and hybrid (BM25 + vector + RRF) using a **baked GloVe-50d model** (3.8 MB embedded, zero deps), with MiniLM / Ollama / OpenAI available opt-in (`README.md:53`).

## How it works under the hood

**Tech stack.** Go 1.26 (`go.mod:1`), CGO for tree-sitter C bindings, cobra CLI, `mark3labs/mcp-go` for MCP, `coder/hnsw` for the vector index, `pkoukk/tiktoken-go` for token counting. Language coverage is **257 languages/grammars** across three tiers — bespoke tree-sitter extractors, regex extractors, and `alexaandru/go-sitter-forest`-backed signatures — plus Jupyter and Databricks notebooks (`README.md:47`).

**Architecture** is a layered in-process engine centered on `internal/graph.Graph` (`plans/docs/architecture.md:24-26`): *"Indexers write to it. Query, analysis, MCP, HTTP, contracts, and daemon sessions read from it."* The graph is sharded 16 ways by FNV hash of node ID for concurrent writes, each shard with its own RWMutex and secondary indexes (`byName`, `byFile`, `byRepo`, in/out edge adjacency, `internal/graph/graph.go:27-109`).

**Package layout** (`internal/`): `parser` (tree-sitter registry + extractors), `indexer` (repo walk, incremental reindex, `MultiIndexer`, `watcher`), `resolver` (cross-file/cross-repo symbol resolution with type inference), `contracts` (provider/consumer matching), `semantic` (SCIP/go-types/LSP enrichment), `search` (bm25, bleve, vector, hybrid), `query` (the traversal `Engine`), `mcp` (tool/resource/prompt server), `server` (HTTP), `daemon` (Unix-socket multiplexer), `persistence` (snapshots + experiential stores), `hooks` (Claude Code hook handlers), `claudemd`/`skills`/`agents` (setup adapters), `savings`/`tokens` (accounting). `pkg/gortex/api.go` is the small public embed API.

**Data flow** (`plans/docs/architecture.md:46-81`): walk files → detect language → extractor emits nodes+edges → coverage passes add todos/licenses/ownership/SQL/configs → apply repo/workspace/project identity → `Graph.AddNode/AddEdge` → resolver retargets unresolved edges to concrete node IDs → optional semantic enrichment upgrades edge confidence → build search index + commit contract registry. All serving surfaces (CLI, MCP stdio, HTTP `/v1`, daemon dispatcher) wrap the same `query.Engine` and `mcp.Server`.

## How memory about a codebase under development is implemented

Gortex's "memory" is layered into **four distinct stores** that map cleanly onto the survey's concepts: a **factual/semantic memory** (the knowledge graph), an *implicit* **experiential memory** (feedback/frecency/combo learning), an *explicit* **agent-authored memory** subsystem (session notes + durable development memories), and a **token-level working-memory injection** layer (generated files + hooks).

### 1. Factual/semantic memory — the knowledge graph (primary)

The core memory is the in-memory graph, its schema fully explicit in `internal/graph/node.go` and `edge.go`. A `Node` (`node.go:157-184`) carries `ID`, `Kind`, `Name`, `QualName`, `FilePath`, `StartLine/EndLine`, `Language`, a `Meta map[string]any` (signatures, docs, visibility, confidence, ownership, coverage — language-specific facts), plus `RepoPrefix`, `WorkspaceID`, `ProjectID` for multi-repo identity. There are ~30 node kinds — not just `function`/`type`/`interface` but `KindModule`, `KindTable`/`KindColumn`, `KindConfigKey`, `KindTodo`, `KindTeam`, `KindResource` (K8s), `KindImage` (Dockerfile) — each with a documented ID convention (e.g. a TODO is `todo::<file>:<line>`, `node.go:88`). An `Edge` (`edge.go:303-323`) records `From`/`To`/`Kind`/`FilePath`/`Line` plus a **confidence tier** in `Origin`: `lsp_resolved` > `lsp_dispatch` > `ast_resolved` > `ast_inferred` > `text_matched` (`edge.go:340-346`). This tier is *the* mechanism that lets agents trust an edge for a refactor — `min_tier` filters restrict traversals to compiler-verified edges. Edge kinds span calls, imports, implements, `reads`/`writes` (field-level), `throws`, `tests`, dataflow (`value_flow`/`arg_of`/`returns_to`), and contract `matches`.

**Where it lives on disk.** Persistence depends on the daemon's `--backend`, which **defaults to `sqlite`** (`cmd/gortex/daemon.go:124`) — a pure-Go embedded SQL store at `~/.gortex/store/store.sqlite` (`--backend-path`, `daemon.go:127`) that holds the graph directly, so a warm restart reads nodes/edges (plus per-file mtimes from a `FileMtime` sidecar table, contract records off `KindContract.Meta`, and the vector index) straight from the store — no gob round-trip (`daemon.go:229-249`). Only the **`memory` backend** uses a **gob+gzip snapshot**: `persistence.Snapshot` (`internal/persistence/store.go`) bundles `Nodes`, `Edges`, `FileMtimes`, and the serialized HNSW `VectorIndex`, written by `FileStore` as `{cacheDir}/{cacheKey}/snapshot.gob.gz` + a `.version` file that invalidates snapshots after a binary upgrade. The snapshot key `CacheKey(repoPath, branch, commitHash)` is keyed by **(repo, branch)** — one slot per branch, overwritten as the branch advances — and falls back to the commit hash only for a detached HEAD (`persistence/key.go:12`), so a warm restart after new commits incrementally reconciles the branch's last graph instead of cold-indexing because the commit moved.

**Lifecycle — creation → evolution → invalidation.** On a warm restart the default SQLite backend reads the graph from its on-disk store (and the `memory` backend replays its gob snapshot when the repo+branch key matches); otherwise Gortex does a full index. Evolution is **incremental**: `IncrementalReindex` (`internal/indexer/indexer.go:1769-1808`) walks the tree, compares each file against stored mtimes via `IsStale`, and re-parses only stale files (~200 ms vs 3–5 s full re-index, `README.md:45`). Watch mode (fsnotify) and a `.git/HEAD` watcher patch the graph surgically on edits and branch switches. This is why it reduces `find`/`rg`: instead of grepping, the agent hits `search_symbols`/`smart_context`, which read the pre-built graph in memory.

### 2. Implicit experiential memory — learning across sessions

Separately from the commit-scoped graph, three stores persist **repo-scoped (cross-commit)** experiential data, each its own gob+gzip file under `RepoCacheKey = sha256(path)[:6] + "_latest"`:

- **Feedback** (`persistence/feedback.go`): `FeedbackEntry{Task, Useful[], NotNeeded[], Missing[], Source}`, capped at 500 entries — records of what worked on past tasks (case/strategy-based experiential memory in the survey's terms).
- **Frecency** (`persistence/frecency.go`): per-symbol access timestamps (bounded deque of 16), scored with an **exponential-decay** formula `score += exp(-k·Δdays)` (`internal/mcp/frecency.go:96-116`) with an AI-vs-human half-life — a recency/working memory of what's been touched.
- **Combo** (`persistence/combo.go`): `query → symbol` hit-count associations, so repeated queries learn their best answers.

The retrieval path fuses factual + experiential memory. In `handleSmartContext` (`internal/mcp/tools_coding.go:1102-1367`): step 2 does BM25 keyword search over the graph; step 3c reranks by `baseScore + feedbackScore*0.3` and **injects frequently-missed symbols** matching the task keywords (`tools_coding.go:1169-1213`); it then embeds signatures and (for the top 3) actual source, expands to callers/callees/tests/files-to-edit, and records `tokens_saved`. Past feedback thus measurably reshapes future context. Cumulative token savings persist to the machine-global SQLite sidecar `~/.gortex/sidecar.sqlite` (the same DB that holds notes, memories, scopes, and notebooks; `internal/savings/store.go:6`); the older flat-file `savings.json`/`savings.jsonl` ledgers are imported once on open and renamed `*.bak` (`docs/savings.md:7`).

### 3. Agent-authored session notes & durable development memories

Beyond the implicit signals above, Gortex ships a **first-class, explicitly-authored memory subsystem** — the daemon's "Layer-2 note / memory verbs" (`cmd/gortex/memory.go:20`), exposed both as MCP tools and as `gortex memory` CLI subcommands, and documented in `docs/features.md:128`. Where feedback/frecency/combo are *learned automatically*, this layer is knowledge the agent (or a human) writes down on purpose.

- **Session notes** — `save_note` / `query_notes` / `distill_session` (CLI: `gortex memory note/notes/distill`). An agent writes a free-text note scoped to a session; it is **auto-linked to the symbols mentioned in its body** (`notes.go`, `AutoLinks`) and may carry an explicit `symbol_id`/`file_path` anchor, tags, and a `pinned` flag. Notes "survive daemon restarts and context compactions," and `distill_session` folds a session's notes into a digest with the top symbols touched. A bounded cap trims the **oldest non-pinned** notes first (pinned notes are never evicted, `sidecar_sqlite.go:468-485`).

- **Durable development memories** — `store_memory` / `query_memories` / `surface_memories`, plus MCP-only `edit_memory` / `rename_memory` (CLI: `gortex memory store/recall/surface`). These are **cross-session, workspace-wide** knowledge entries, each typed by `kind` (invariant / constraint / convention / gotcha / decision / incident / reference), with `importance` (1..5), `confidence` (0..1), an author agent, tags, and **anchors** — `symbol_ids` + `file_paths` (plus auto-links). This is the survey's *experiential/semantic memory* made explicit and human-editable: the durable "why" a team accumulates about a codebase, rather than a signal inferred from tool usage.

- **Symbol/file anchoring & proactive surfacing.** `surface_memories` is what makes this working-set-relevant. Given a task's anchor symbols/files, `memoryManager.Surface` (`internal/mcp/memories.go:428-600`) ranks candidates by a transparent additive score: **+3.0** per anchor-symbol overlap with a memory's `symbol_ids`, **+1.5** per overlap with its auto-links, **+1.5** per anchor-file overlap with `file_paths`, **+0.5 × importance**, **+0.3** if updated within 30 days, **+0.2** if already proven useful (`access_count > 0`), then the whole score **× confidence**. Anchor symbols are promoted to their containing files automatically (a free signal). With anchors present, a memory must match at least one reason (pinned counts) to surface; with none, every memory returns ranked by importance + recency. Surfacing stamps `access_count`/`last_accessed`, which feeds the "proven useful" boost next time — the docs describe memories as "surfaced proactively … when anchor symbols / files enter the working set."

- **Supersession & editing.** Memories are mutable and versionable: `edit_memory` patches fields, `rename_memory` changes the ID, and a `superseded_by` pointer (schema column, `sidecar_sqlite.go:95`) marks a memory replaced by a newer one — queries hide superseded entries by default (`IncludeSuperseded=false`, `memories.go:97,276,496`). This is the survey's *updating / forgetting* dynamic (§5.2) done explicitly rather than by TTL.

- **Sidecar persistence.** All of this lives in the **machine-global SQLite sidecar** `~/.gortex/sidecar.sqlite` (`internal/persistence/sidecar_sqlite.go:16`) — a **separate database from the graph store**, independent of the graph `--backend`, so notes/memories/scopes/notebooks persist even when the graph runs in the `memory` backend. Rows are scoped by `repo_key` (the same `RepoCacheKey` hash), so one sidecar file holds every served repo's notes and memories; the same file also backs the savings ledger, saved scopes, and the git-committed repository **notebook** (`notebook_save` / `notebook_find` / …).

### 4. Token-level working memory — injection into the prompt

The graph is useful only if it reaches the model's context. Gortex injects it three ways:

- **MCP tools/resources** — pull-based; the agent calls `smart_context`, `get_symbol_source`, etc., returned as JSON or the compact **GCX1 wire format** (an additional −27% tokens vs JSON at the same fidelity, `README.md:56`).
- **Generated static files** — `internal/claudemd/generator.go:13-60` writes a `## Codebase Overview` block into `CLAUDE.md` (primary language, entry points, most-referenced symbols, node/edge counts), plus marker-guarded (`<!-- gortex:communities:start/end -->`) community-routing tables, and per-community `SKILL.md` files. This is durable, VCS-shareable memory the agent reads every session.
- **Claude Code hooks** — push-based context injection (`internal/hooks/`). **PreToolUse** intercepts `Read`/`Grep`/`Glob`/`Bash` and redirects the agent to graph tools (`pretooluse.go:18-45`). **PreCompact** queries `graph_stats` and emits an `additionalContext` orientation snapshot *before the conversation is compacted*, so the agent "survives compaction without having to re-explore" (`precompact.go:26-58`) — a direct working-memory-preservation mechanism. **Stop** runs post-task diagnostics (test targets, guard violations, dead code, contract checks). All hooks degrade silently if the server is unreachable.

### Memory-form summary

In the survey's terms, the graph is **token-level factual/semantic memory** (external, non-parametric, explicitly retrieved — nothing baked into model weights; it is "latent" only insofar as the HNSW embeddings encode symbols in vector space). Two flavors of **experiential memory** sit alongside it: the *implicit* feedback/frecency/combo stores that bias retrieval over time, and the *explicit*, agent-authored **session notes and durable development memories** (typed, anchored, superseding) that record a team's accumulated "why." The generated `CLAUDE.md`/skills, the PreCompact/PreToolUse hooks, and `surface_memories` form the **working-memory injection layer** that moves the right slice into the live context window. No parametric memory is used — Gortex never fine-tunes a model; all memory is externalized — the embedded SQLite graph backend (or a gob+gzip snapshot under the `memory` backend), the gob+gzip experiential stores, the machine-global SQLite sidecar (notes / memories / notebook / savings), and generated markdown — and retrieved on demand.
